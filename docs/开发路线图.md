# NetScope 开发路线图

> 依据《Windows 轻量系统活动监视与性能黑匣子开发方案》整理，对照 NetScope V0.6 本地开发版，给出产品定位、差距分析、设计边界、版本规划与验收标准。

## 1. 产品定位

**一个轻量、常驻、带历史记录和自动归因能力的 Windows 系统活动监视器（性能黑匣子）。**

它不是任务管理器、不是端口管理器、也不是“一键优化”工具。产品要回答的核心问题始终是：

- 刚才电脑为什么卡？
- 是谁造成的？
- 这个进程是什么？
- 这种情况是不是经常发生？
- 我需不需要处理它？

统一对象模型：

```text
Process ↔ Resource ↔ Port ↔ Connection ↔ Event ↔ Diagnosis
```

进程是系统活动图谱的核心实体：一个进程同时挂载资源占用、端口、连接、历史事件与卡顿相关性，而不是任务管理器里的“一行”。

## 2. 三条产品原则

1. **Observe First（先观察）**：默认只记录——谁启动了、谁连了网、谁在监听、谁突然占资源、持续多久、是否与用户感知卡顿重合。不结束进程、不改启动项、不动注册表。
2. **Explain Second（再解释）**：不只给数字（`MsMpEng.exe CPU 68%`），而是给“发生了什么、与谁相关、证据是什么、有多大把握、建议怎么做”。所有结论使用“可能/疑似”语义并附证据与可信度。
3. **Intervene Only When Requested（仅应要求干预）**：任何干预动作（结束/重启/释放端口）都必须由用户显式点击触发，系统永不“一键优化”。

## 3. 当前位置（截至 V0.6 本地开发版）

对照方案的推荐开发优先级（§76）逐项核对：

| 优先级 | 方案要求 | NetScope 状态 |
|---|---|---|
| 一 | 低开销 Collector | ✅ V0.2 用户级后台进程（命名管道 IPC，单实例），1s/2s 采样，异常后 500ms 突发 30–60s |
| 一 | 统一 Process Registry（PID+启动时间） | ✅ V0.2 `ProcessInstanceKey`，PID 复用不串历史 |

| 一 | Ports | ✅ V0.1.5 端口工作台（实时占用/端口百科/可用端口） |
| 一 | History（环形缓冲→SQLite→降采样） | ✅ V0.2 WAL+批量写+保留 1/7/14/30 天+30s 降采样+损坏恢复 |
| 二 | Timeline | ✅ V0.2 性能页总览曲线 + 事件时间线（前 30s→中→后 30s） |
| 二 | Event Detection（阈值规则） | ✅ 4 规则（CPU/内存/IO/网络）+ 正常→疑似→捕捉中→冷却状态机 |
| 二 | “刚才卡了” | ✅ V0.2 用户标记事件 + 归因邻近加权 |
| 二 | Event Detail / Process Activity | ✅ 事件详情（证据/建议/关联进程）+ 进程中心（曲线/相关事件/端口） |
| 三 | Impact Score | ✅ 单事件口径（CPU+内存+IO+前台+用户标记）+ 7 天聚合口径（V0.3 影响排行） |
| 三 | GPU 监控 | ❌ 明确暂缓（见 §5） |
| 三 | System Process Knowledge | ✅ 基础版（V0.3：34 条系统进程知识库 + 第三方签名/发布者识别） |
| 三 | Automatic Attribution | ✅ 规则+统计归因，证据驱动、附可信度 |
| 四 | Periodic Detection / Memory Leak / Advanced ETW / DPC | ✅ V0.5 已完成周期行为与内存增长；ETW/DPC 仍暂缓 |

**结论：V0.3–V0.6 规划功能已在本地开发版落地，包含 V0.4 分析深化、V0.5 自监控与长期行为、V0.6 可回查 Insights。下一步是完成真实 24 小时/整机压力验收后发布，再进入 V1.0。**

## 4. 差距清单（Gap）

> 本节保留 V0.2 时点的差距分析；知识库、第三方识别、端口历史与 7 天排行已在 V0.3 完成，相对 CPU 检测、评分、连接表和磁盘增强已在本地 V0.4 实现。当前待办以第 6 节版本清单为准。

### 数据面
- **进程级网络带宽**（每进程 rx/tx）：需要 ETW；当前只有系统级收发速率。
- ✅ **连接表**：V0.4 已用 IP Helper 快照差分维护远端 IP/端口、状态和观察起止时间。
- ✅ **磁盘延迟/队列/Active Time**：V0.4 已通过 PDH 物理磁盘合计计数器加入判定。
- **GPU**：D3DKMT 文档化 API 可实现，暂缓。

### 分析面
- ✅ **相对异常检测**：V0.4 已实现 EWMA 与中位数/MAD 基线。
- ✅ **系统响应性评分**：V0.4 已实现 0–100 资源压力启发式评分。
- ✅ **7/30 天聚合**：V0.3 提供 7 天 Impact 排行；V0.6 Insights 提供最长 30 天汇总。
- ✅ **周期性后台行为发现**：V0.5 已实现动态阈值、活动段与周期离散度判定。
- ✅ **内存增长趋势检测**：V0.5 已实现按进程实例隔离的稳健趋势判定。

### 知识面
- **进程身份知识库**：Windows 系统进程说明（是什么/为什么运行/能否结束/高占用意味着什么）。
- **第三方进程识别**：数字签名、发布者、产品名（必须带元数据缓存）。
- **端口历史**（“为什么 8080 总被占用”）。

### 工程面
- ✅ **自监控开销展示**与 Self Impact Guard：V0.5 已显示开销并以滞回方式自动降/升频。
- ✅ **长列表虚拟化**与元数据懒加载：V0.5 已对主要长列表启用 Recycling，并保留选中后异步识别。

## 5. 设计边界与已记录偏差

**不做清单（长期有效）**：杀毒、木马扫描、垃圾清理、注册表清理、驱动更新、DNS/游戏加速、软件商店、一键优化、自动关闭 Windows 服务。

**当前明确排除**：
- **ETW**：V0.2 起未使用。若 V0.5+ 引入，仅限低成本 Provider（进程生命周期、每进程网络），默认关闭、异常时短时开启（Burst Trace），并在设置中明确告知。
- **GPU 监控**：暂缓；D3DKMT 作为远期可选项。
- **内核驱动**：不做（开发/签名/蓝屏/审核风险）。
- **Windows 服务**：保持用户级进程；未来若加入干预动作，只对用户自有进程生效，不引入管理员常驻。

**与方案的技术偏差（决策而非缺陷）**：

| 方案建议 | NetScope 实际 | 理由 |
|---|---|---|
| C++20 Core + C# WinUI 3 | .NET 10 全栈（WPF） | 单一技术栈、开发效率高；Collector 实测开销可接受，后续用性能预算约束 |
| Protobuf 序列化 | 长度前缀 UTF-8 JSON | 管道协议简单、可调试、体积可控 |
| ETW 维护进程生命周期 | 快照差分（PID+启动时间身份） | 无需管理员、实现简单；轮询成本已被 90 项测试与冒烟验证 |
| 10min:1s / 24h:5s / 7d:30s / 30d:5min 多级精度 | 热数据 1s（系统）/5s（Top25 进程）+ 超 24h 降采样 30s | 与方案精神一致；30 天 5 分钟口径待 V1.0 |
| GUI 提供 Kill/Restart/Release | 全程只读 | 隐私安全边界；干预功能待用户明确要求时再评估 |
| GUI 6 主入口（Overview/Processes/Performance/Network/Ports/Events） | 端口/性能/诊断/设置 4 入口（性能内含 3 子页） | 从端口工具演进而来的信息架构；随功能增加再收敛 |

## 6. 版本规划

### V0.3 —— 进程知识库与长期影响（对应方案 MVP 0.3）

目标：从“记录了什么”走向“这是什么、影响多大”。

- ✅ 进程身份知识库（已做）：内置 34 条 Windows 常见系统进程说明（svchost/dwm/MsMpEng/SearchIndexer/lsass/audiodg/System 等），含“是什么、为什么运行、高占用意味着什么、能否结束”；进程中心详情面板直接展示。
- ✅ 第三方进程识别（已做）：数字签名（嵌入式 + Windows 目录两级本地验证）、发布者、产品名、文件描述；元数据缓存键 = 可执行路径+修改时间+大小，内存 + 磁盘 JSON 两级，文件未变不重复验证。
- ✅ 端口占用史（已做）：`PortSessionTracker` 对端口快照差分生成会话（连续两次出现开启、消失/换主结束，过滤非 Listen TCP 与瞬态 UDP），SQLite `PortSessions` 表存储，端口详情展示“过去 7 天谁占过、几次、累计多久”。
- ✅ 7 天 Impact 排行（已做）：`ImpactRankingCalculator` 聚合历史事件——频率 45%（15 次封顶）+ 累计时长 30%（2 小时封顶，按贡献者影响分分摊）+ 卡顿标记重合 25%（4 次封顶）；概览页展示 Top 5 榜单。

验收：知识库覆盖常见系统进程；签名验证有缓存（第二次打开不重复验证）；能回答“过去 7 天谁最可能拖慢我的电脑”。

### V0.4 —— 分析深化（本地开发版已实现，尚未发布）

- ✅ 相对 CPU 异常检测：EWMA + Robust Z-Score（中位数/MAD），按进程实例基线判定突增；30 秒学习、5 秒持续与冷却。
- ✅ 系统响应性评分（0–100）：综合 CPU 饱和、内存压力、磁盘、前台进程与用户标记；附扣分证据与缺失指标说明。
- ✅ 连接表：IP Helper 快照差分维护 IPv4/IPv6 TCP 连接、SQLite 历史及查询分组；起止为观察边界，可能漏掉短连接。
- ✅ 磁盘判定增强：PDH 物理磁盘合计延迟/队列/Active Time；低吞吐高延迟也可触发，指标缺失时显式降级。

验收进度：143 项测试通过，包含合成相对 CPU 突增/低吞吐磁盘卡顿、真实 Windows PDH 采样、真实 TCP 回环连接和旧库迁移；WPF 大小窗口渲染检查通过。整机压力注入、长期后台开销预算仍需专项验收，不能以单元测试代替。详见 [V0.4 实现说明](V0.4实现说明.md)。

### V0.5a —— 自监控

- ✅ 性能页常驻展示 Collector 自身 CPU/内存/磁盘写入与采样延迟。
- ✅ Self Impact Guard：Collector 连续超出性能预算时自动降低进程/端口采样频率，恢复后分级升频；所有降频与恢复均留本地记录。
- ✅ 长列表虚拟化、文件元数据与签名信息懒加载，避免 GUI 自身影响被观察系统。

验收进度：自动化故障注入已覆盖四类预算、分级降频、严重降频、滞回恢复与边界值；真实 24 小时常驻预算仍需按墙钟时间执行。

### V0.5b —— 趋势与周期检测

- ✅ 周期性后台行为发现（Updater/遥测/OEM/云同步类软件的周期性活动）。
- ✅ 内存增长趋势检测（长期单向增长判定，明确不等同于泄漏定论）。
- （可选）GPU 监控（D3DKMT，区分 3D/Copy/解码/编码引擎）。
- （决策点）评估引入受限 ETW：进程生命周期 + 每进程网络，默认关闭。

验收进度：合成周期负载、规则/不规则突发、持续高负载、稳定增长、锯齿型缓存和进程重启场景均已覆盖；结论附观察窗口、样本数和置信度。GPU 与 ETW 为可选决策项，本版未启用。

### V0.6 —— Insights

- ✅ Insights 页面智能总结月度卡顿统计（例如“30 天标记 17 次，11 次与 X 有相关证据”）。
- ✅ 汇总相对异常、周期行为、内存趋势、端口和连接变化；只基于已记录证据生成可回查结论。
- ✅ 提供时间范围、进程与事件类型筛选，并可跳转到原始事件、进程曲线或连接记录。

验收进度：事件洞察保留原始 GUID，趋势洞察保留模型与样本证据；空数据及证据不足测试通过。完整记录见 [V0.5–V0.6 实现说明](V0.5-V0.6实现说明.md)。

### V1.0 —— 完整闭环

- 30 天历史（5 分钟粒度聚合）。
- 归因链强化：事件 → 候选进程 → 证据 → 根因假设 → 置信度，全链路可回放。
- 周/月报告。
- 端到端验收场景：真实卡顿 → 点“刚才卡了” → 打开事件 → 看到主相关进程、前后指标对比、30 天内同类行为次数与标记重合次数。

### V1.1 —— 受控干预

- 进程中心增加“请求关闭”和“强制结束”，仅由用户在前台显式触发，永不自动执行。
- 结束建议分为“禁止结束 / 强烈不建议 / 谨慎 / 通常可以结束 / 无法判断”，分别评估系统稳定性与数据/功能中断风险。
- `IsProcessCritical`、进程所有者/会话、服务归属、路径/签名与 PID+启动时间共同参与判断；执行前重新核对身份，防止 PID 复用误杀。
- 正常关闭优先；强制结束只对证据完整的当前用户非关键进程开放。不提权、不结束服务、不结束进程树。
- 执行位于前台 App，不向 Collector IPC 暴露终止能力；结果写入本地审计历史。

详细设计、交互与验收标准见 [进程终止功能设计](进程终止功能设计.md)。

### 远期（按需评估）

- ETW 深化（Context Switch / File IO / Page Fault / DPC / ISR，仅 Burst 模式）。
- 进程重启与端口释放（结束进程已进入 V1.1；其余动作需要独立评估）。
- 开机慢分析、睡眠唤醒来源、电池消耗排行、崩溃分析、DPC/驱动延迟。

## 7. 性能预算与验收标准

Collector：

- 空闲平均 CPU < 0.3%（追求 0.1–0.2%），P95 < 1%；
- 内存 < 50 MB；
- 常态磁盘写入 < 5 MB/小时；
- GUI 关闭时零渲染开销（Collector 独立运行）。

GUI：

- 托盘点击到首帧只读 State Snapshot：不扫描、不验证签名、不全量加载图标、不做 DNS 反查；
- 长列表虚拟化（只渲染可见 20–40 行），图标异步加载；
- Remote IP 第一阶段直接显示，反查 DNS 异步且可关闭。

Observer Effect 验证：Collector ON / OFF 对比整机 CPU、IO、延迟与基准测试，产品必须证明自己的观测开销足够小。

## 8. 核心测试场景（每版回归）

| 场景 | 注入方式 | 预期 |
|---|---|---|
| CPU 争用 | 压测进程占满若干核心 | 检测 + 定位 PID + 生成事件 |
| 磁盘压力 | 大量随机小 IO | IO 压力事件（V0.4 起含延迟/队列证据） |
| 内存压力 | 持续申请内存 | 内存压力事件（V0.5 起含增长趋势证据） |
| 网络突发 | 大文件下载 | 网络吞吐抬升进入证据链 |
| 端口绑定 | 启动 localhost:5000 | PID/可执行文件正确关联到端口 |
| 用户标记 | 点击“刚才卡了” | 事件落库 + 归因排序包含时间邻近进程 |

## 9. 风险与决策点

1. **ETW 引入时机**：每进程网络带宽与精细归因都依赖 ETW。决策点放在 V0.5——默认关闭、异常时短时开启、设置中明确告知，且不与“数据仅存本机”的隐私承诺冲突。
2. **数据库体积**：30 天口径需压测降采样与保留策略，控制在数百 MB 内。
3. **只读边界**：干预功能与产品原则存在张力；若引入，必须是显式确认的独立动作，绝不演化成“一键优化”。
4. **权限模型**：保持用户级运行；不因功能便利引入管理员常驻或服务化。
5. **GUI 复杂度**：功能增加时保持主入口数量克制，优先把 Insights 做成 Overview 内的智能总结而不是新增顶级页面。
