# NetScope 架构说明（As-Built）

> 记录 V0.6 本地开发版的实际架构：组件划分、数据流水线、IPC 协议、采样与调度模型、事件引擎、长期行为、Insights、历史存储与安全边界。所有条目与代码一一对应；产品定位与版本规划见[开发路线图](开发路线图.md)。

## 1. 总体结构

```text
┌────────────────────────────┐         ┌──────────────────────────────────┐
│ NetScope.exe（WPF GUI）     │         │ NetScope.Collector.exe（后台常驻）│
│                            │         │                                  │
│  PortViewModel   端口工作台 │         │  Program：命名互斥单实例          │
│  PerformanceViewModel 性能 │ ◀─IPC─▶ │  CollectorHost：组装与设置热重载   │
│  DiagnosticViewModel 诊断  │ 命名管道 │  ├ SampleCoordinator 采样循环     │
│  SettingsViewModel   设置  │         │  ├ PerformanceEventEngine 事件    │
│                            │         │  ├ SqliteHistoryStore 历史落盘    │
│  CollectorLauncher 启动/探测│         │  └ CollectorIpcServer 管道服务端  │
└────────────────────────────┘         └──────────────────────────────────┘
        ▲ 仅查询/渲染/交互                        ▲ 采集/事件/存储（无 GUI）
        └──────────── 共享 ─────────────┐
                                       ▼
                    NetScope.Core（模型/规则/评分）
                    NetScope.Windows（Win32 采集/IPC/SQLite/设置/日志）
```

- GUI 不参与采集（方案 §39）：关闭主窗口后 Collector 继续采样、记录、检测事件；再次打开时 GUI 直接读取 Collector 当前状态，无需全量重扫。
- App 启动时由 `CollectorLauncher.EnsureRunningAsync` 先探测管道，未就绪则启动同目录 `NetScope.Collector.exe --background`。两者同目录发布（`scripts/package.ps1` 校验 Collector exe 存在）。

## 3. 进程身份（方案 §7）

```csharp
readonly record struct ProcessInstanceKey(int ProcessId, DateTimeOffset StartedAt);
```

- PID 不作唯一 ID：Windows 会复用 PID，必须叠加进程启动时间。
- 采样、历史表主键、事件贡献者、进程历史查询全部以该身份键控，同一 PID 的先后实例历史互不串扰（有专门测试覆盖）。
- 进程枚举按轮差分：新 PID 首见输出零速率占位，消失即从状态字典清理——不需要 ETW 也能维护“当前存活的进程集合”。

## 4. 采样与调度模型（方案 §67-68 的简化实现）

`SampleCoordinator` 用**单个采样循环**驱动全部模块（对应方案 §66 “不要每模块一线程”）：

| 项目 | 周期 | 说明 |
|---|---|---|
| 系统采样 | 1s | CPU（累计时间差量）、可用/总内存、活动网卡收发字节差量；网卡链路状态为被动判定 |
| 进程采样 | 1s | 全进程枚举，按实例身份与上一轮读数差量换算 CPU%/IO Bps；记录采样瞬间前台 PID |
| 端口采样 | 2s | TCP/UDP v4/v6 绑定快照（`tick % 2`），供端口页与进程“监听端口数” |
| 突发采样 | 500ms | 事件触发或用户点“刚才卡了”后持续 30s；期间历史落盘粒度同步提高到 500ms |
| 历史落盘 | 常规 5s | 每轮写系统采样 + 影响分 Top25 进程（控制体积的已记录偏差） |

内存态：

- `MemoryRingBuffer<SystemPerformanceSample>`：3600 条（1 小时 1s 精度）；
- 进程环形缓冲 28800 条；
- 内存事件列表上限 500 条（按开始时间排序，同 Id 事件以最新状态替换）。

设置开关：`BackgroundRecording=false` 时采样循环整体空转（仅保留端口 2s 刷新，端口页不受影响）。

## 5. IPC 协议（方案 §39 的 JSON 实现）

- 传输：命名管道 `NetScope.Collector.v3`，字节模式，服务端最大并发实例 8，每连接独立 Task 处理。
- 帧：`PipeFrame` = 4 字节小端长度前缀 + UTF-8 JSON。
- 信封：`IpcEnvelope { Op, RequestId, Ok, Error, Json }`；服务端异常以 `Ok=false + Error` 返回，不中断连接。
- 握手：每连接首条消息必须 `hello`，协议版本不匹配即断开（`ProtocolVersion=2`，`ServerVersion=0.6.0`）。
- 操作集：

| Op | 载荷 | 返回 |
|---|---|---|
| `ping` | — | `"pong"` |
| `system` | — | 最新系统采样 |
| `processes` | — | 最新全量进程采样 |
| `ports` | — | 最新端口快照 |
| `events` | `{limit}` | 最近事件（≤500 条，见 §7 查询策略） |
| `systemHistory` | `{from,to}` | 历史系统采样 |
| `processHistory` | `{processId,startedAt,from,to}` | 按进程身份查历史 |
| `markLag` | — | `{startedAt,accepted}` |

- App 侧 `CollectorClient` 采用**每请求短连接**（连接→hello→一问一答→断开），避免长连接状态管理；`NullCollectorClient` 为 `--no-collector` 模式的空实现，UI 全部降级为“未连接”文案。

## 6. 事件引擎（方案 §21-34 的第一阶段实现）

`PerformanceEventEngine`，四条规则 × 状态机 `Normal → Suspected → Capturing → Cooldown`：

| 规则 | 条件（默认） | 持续 | 主关联进程 |
|---|---|---|---|
| CPU 争用 | 系统 CPU ≥ 85% | 10s | 期间平均 CPU 最高的可访问进程 |
| 内存压力 | 可用内存 <10% 或 <512MB | 10s | 期间工作集最大的进程 |
| I/O 压力 | 全机进程读写合计 ≥80MB/s | 10s | 期间读写合计最高的进程（结论只到“疑似”，进程 IO 计数≠磁盘延迟） |
| 网络退化 | 活动网卡链路断开 | 10s | 无（被动状态证据） |

关键语义：

- **持续阈值**：条件持续满足才建事件（防止瞬时尖峰误报）；条件一旦消失立即关闭（`EndedAt`=首个未命中 tick）。
- **冷却**：同类事件关闭后 120s 内不重复创建，防事件风暴。
- **证据累积**：条件持续期间逐 tick 记录峰值/末值与 Top 贡献进程（上限 5），关闭时输出完整证据链。
- **用户标记加权**：`NoteUserMark(t)` 让点击“刚才卡了”前后 ±60s 窗口内的进程在 Impact 排序中获得邻近度加成。
- **Impact Score**（`ImpactScoreCalculator`）：CPU≤40 + 内存≤25 + IO≤25 + 前台+10 + 标记邻近≤15，封顶 100。**只做证据排序，不下因果结论**；所有文案使用“可能/疑似”并附可信度。
- 触发事件后 `SampleCoordinator.RequestBurst(30s)` 自动进入突发采样。

## 7. “刚才卡了”（方案 §25-26 的 V0.2 口径）

`CollectorHost.MarkLagAsync`：

1. `NoteUserMark(now)` 登记标记时刻（供归因加权）；
2. `RequestBurst(30s)` 进入高精度采样；
3. 锁定前 60 秒现场（内存环形缓冲 + 高精度历史），合成一条 `UserMarkedLag` 事件（可信度 100），写历史并推入内存事件列表。

事件查询策略：优先查 SQLite（保留期内），库不可用（已关闭/损坏重建中）回退内存列表——时间线在两种状态下都可用。

## 8. 历史存储（方案 §16-18 的实现）

`SqliteHistoryStore`（Microsoft.Data.Sqlite）：

- 位置：`%LocalAppData%\NetScope\data\netscope.db`；PRAGMA `journal_mode=WAL` + `synchronous=NORMAL`。
- 并发：`SemaphoreSlim(1,1)` 串行化所有访问（注意：不可重入，恢复路径拆分为持锁外壳 + 无锁核心）。
- 写入：内存 `ConcurrentQueue` 攒批，后台 flush 循环批量写；队列有界 20,000 条，积压丢最旧——Collector 永不因写盘阻塞采样。
- 表：`SystemSamples`、`ProcessSamples(进程身份+时间索引)`、`PerformanceEvents`、`EventContributors`、`PortSessions`、`TcpConnections`、`CollectorHealth`。
- 保留：1/7/14/30 天（默认 7），每次 flush 顺带清理过期行；上限夹紧 1–30。
- 降采样：查询跨度 >24h 时按 30 秒桶聚合（每桶取首样本），控制返回体积。
- 损坏恢复：初始化或写入失败时 `PRAGMA quick_check`；确认损坏则把库文件备份为 `netscope.db.corrupt-时间戳` 后重建空库——实时采样与内存事件不受影响。
- 门控：`ConditionalHistoryStore` 包装器按设置（`HistoryEnabled && BackgroundRecording`、保留天数）决定是否新增写入；关闭后仍可查询已有本地记录。

设置热重载：Collector 每 15s 重读 `settings.json`，变化即生效（含历史开关/保留天数/后台采样），无需重启——UI 与 Collector 之间除 markLag 外没有反向控制通道，靠文件约定解耦。

## 9. GUI 结构

- 导航四入口：**端口**（默认首页）/ **性能** / **诊断** / **设置**；性能内含概览、事件时间线、进程中心、Insights、TCP 连接五个子页。
- 刷新：性能页两个 `DispatcherTimer`——2s（系统+曲线，每 2 tick 刷进程列表）与 8s（事件）；页面离开（`OnHidden`）即停表，空闲零 IPC。
- 曲线：三套独立集合（总览 15 分钟 / 事件上下文 ±30s / 进程详情 15 分钟），`SparklineVisual` 支持空态文案。
- 只读：全部操作只查询与标记，无结束进程/改配置入口。

## 10. 安全与隐私落地

| 承诺 | 代码层落地 |
|---|---|
| 数据仅存本机 | 唯一持久化为 SQLite 历史与 settings.json，均在 `%LocalAppData%\NetScope`；无任何网络上传路径 |
| 只读 | Collector/App 无终止进程、无注册表/防火墙/系统配置写入（`StartupRegistration` 仅在用户显式开启自启时写 Run 键） |
| 脱敏日志 | `RollingFileLogger` 3×1MB，URL/SSID/MAC/IP 形态脱敏 |
| 可关闭 | 历史记录、后台采样均可在设置关闭，15s 内生效 |
| 可诊断 | 损坏库自动备份重建；事件查询有内存回退；`--no-collector` 模式完整可用 |

## 12. 已知限制清单（诚实边界）

1. 历史仅持久化影响分 Top25 进程（5s 粒度）；长尾进程只有内存态。
2. 突发采样是全局模式（500ms 对所有采样对象），非按进程触发。
3. 网络退化规则为被动链路状态，通常只有状态证据、无主关联进程。
4. 进程 IO 计数 ≠ 磁盘延迟，I/O 压力结论永远带“疑似”与相应建议文案。
5. 每进程网络带宽与 GPU 未实现；TCP 连接为轮询观察，可能漏掉短连接。
6. 24 小时真实常驻预算和整机 Collector ON/OFF 对照尚未执行，当前只有加速时间轴与进程内故障注入。
